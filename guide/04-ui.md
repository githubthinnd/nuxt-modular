# 4. User interface

## Outlets: `<PluginOutlet>`

An outlet is a named place in the host where extensions render components.

```vue
<PluginOutlet name="course.tabs" :context="{ courseId }" />

<PluginOutlet name="course.sidebar" wrap-with="aside" item-tag="section">
  <template #empty>Nothing here yet.</template>
  <template #fallback="{ extensionId, error }">{{ extensionId }} failed.</template>
</PluginOutlet>
```

| Prop | Type | Description |
|------|------|-------------|
| `name` | `string` | Outlet id, dot-namespaced (`course.tabs`). Required. |
| `context` | `object` | Handed to every extension component as the `context` prop. Static `props` from the manifest are spread alongside. |
| `wrapWith` | `string \| Component` | Element or component wrapping the whole outlet. Not rendered when the outlet is empty. Gets `data-outlet="<name>"`. |
| `itemTag` | `string` | Tag of each item's wrapper (default `div`; use `li` inside a list). |

| Slot | When |
|------|------|
| `#empty` | No active, permitted extension contributes to the outlet. |
| `#fallback` | Replaces the default error UI of a failed extension component. Props: `extensionId`, `slotKey`, `error`. |

**Name your outlets like an API.** Outlet names are the contract between host and extensions. Use stable,
dot-namespaced names (`dashboard.metrics`, `course.tabs`) and document the `context` each one provides.

Every item is wrapped in an element styled `display: contents`, so it does not affect your layout. Inside tables or
lists choose a wrapper that is valid there with `item-tag` (for example `li`).

### Writing a slot component

An ordinary Vue component. It receives the manifest's static `props` and the outlet's `context`:

```vue
<!-- extensions/quiz/components/QuizTab.vue -->
<script setup lang="ts">
defineProps<{ title?: string; context?: { courseId: string } }>()
</script>

<template>
  <section>
    <h2>{{ title ?? 'Quiz' }}</h2>
    <p>Course {{ context?.courseId }}</p>
  </section>
</template>
```

Extension components are lazy-loaded chunks: they do not weigh on pages whose outlets do not show them.

## Ordering

Items in an outlet are sorted by `order` ascending, then by extension id, then by declaration order. The result is the
same on every server and every browser, which is what keeps hydration clean.

## Navigation

Navigation items are declared flat in each manifest; the registry assembles the tree.

```ts
const registry = useModuleRegistry()
const tree = computed(() => registry.getNavigation('sidebar'))  // NavigationNode[]
```

Each node has `id`, `label`, `path`, `icon`, `order`, `permission`, `extensionId` and `children`. Items of inactive
extensions, items the viewer may not see, and all descendants of a hidden item are left out.

A recursive menu component:

```vue
<!-- components/NavTree.vue -->
<script setup lang="ts">
import type { NavigationNode } from '#modular'
defineProps<{ items: readonly NavigationNode[] }>()
</script>

<template>
  <ul>
    <li v-for="item in items" :key="item.id">
      <NuxtLink v-if="item.path" :to="item.path">{{ item.label }}</NuxtLink>
      <span v-else>{{ item.label }}</span>
      <NavTree v-if="item.children.length" :items="item.children" />
    </li>
  </ul>
</template>
```

`parent` is either a host menu id you choose (`sidebar`, `navbar`) or the id of another navigation item (for nesting).
Navigation ids must be unique across all extensions; a clash fails the build.

## Pages

Files in `extensions/<id>/pages/` become routes, following Nuxt conventions:

| File | Route |
|------|-------|
| `pages/quiz/index.vue` | `/quiz` |
| `pages/quiz/[id].vue` | `/quiz/:id` |
| `pages/docs/[...slug].vue` | catch-all |

- Route names are `ext-<id>-<path>` and every route carries `meta.modularExtension = '<id>'`.
- **The host wins.** If a host page already serves the same path, the extension page is skipped and the build warns.
- A page of an inactive extension answers **404**.
- Page-level features (`definePageMeta`, `useHead`, `useFetch`) work as in any Nuxt page.

## Plugins

Files directly under `extensions/<id>/plugins/` are registered as Nuxt plugins, with the usual `.client.ts` / `.server.ts`
suffixes. They exist only when the extension is part of the build. They run for visitors regardless of persistent
toggles; check `useModuleRegistry().isModuleActive('<id>')` inside if you need to.

## Components

`extensions/<id>/components/` is registered like Nuxt's own `components/` folder (names follow the path:
`quiz/Tab.vue` → `QuizTab`). Use them in the extension's pages and slot components.

## Error isolation

Each slot renders inside its own boundary:

- **During SSR** an error is recorded in the payload and swallowed; the rest of the page renders and the visitor
  receives valid HTML.
- **During hydration** a slot that failed on the server adopts the server markup as-is (no mismatch) and switches to
  the fallback after mount.
- **After hydration** the fallback replaces the component immediately.
- Errors are logged to the console with the extension id, outlet and slot.

Customize the fallback with the `#fallback` slot of `<PluginOutlet>`. An error that happens *only* in the browser while
hydrating still produces one Vue hydration warning, because the server and the client genuinely rendered different
content.

## Registry composable

```ts
const registry = useModuleRegistry()

registry.extensions.value                // [{ id, manifest, active, source, persistedOverride, sessionOverride, missingDependencies }]
registry.getSlotComponents('course.tabs')
registry.getNavigation('sidebar')
registry.isModuleActive('quiz')
registry.setModuleActive('quiz', false)  // this request / tab; null restores the default
registry.register(manifest)              // runtime registration (its components must be in the build)
registry.unregister('id')                // runtime-registered extensions only
registry.capabilitiesForRoles(['teacher'])
```

State lives in `useState`, so server and client agree.
